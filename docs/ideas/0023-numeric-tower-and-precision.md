# 0023. Числовая башня и точность

**Статус:** идея
**Сложность:** высокая

## Что есть в Java, но не в C++

Java-прототип поддерживает шесть числовых типов:

| Тип | Представление в Java | Смысл |
|-----|----------------------|-------|
| `natural` | `BigInteger` | неотрицательное целое |
| `integer` | `BigInteger` | целое |
| `rational` | два `BigInteger`, сокращённые | обыкновенная дробь |
| `real` | `BigDecimal` + `MathContext(4, HALF_UP)` | десятичная дробь |
| `gaussian` | два `FInteger` | комплексное целое `a + bi` |
| `complex` | два `FReal` | комплексное с действительной/мнимой `real` |

В C++ сейчас:

- `Value` — это `std::variant<Natural, Integer>`;
- оба типа хранят `long long` и ограничены `kLimit = 1e18`;
- `ValueType` уже перечисляет `Rational`, `Real`, `Complex`, `Gaussian`, но
  `Value::of` для них бросает `invalid_argument`;
- `canPass` знает только расширение `natural -> integer`;
- `commonType` для пары чисел даёт `natural`, только если оба natural, иначе
  `integer`;
- `div`/`mod` на ноль возвращают `0`, `pow` насыщается на пределе, а `abs`
  реализован как бинарная функция.

Это осознанное упрощение: решатель и старые уровни работают на целых. Но
документация уже упоминает НОД/НОК и большие числа, а Java-уровни могут
использовать рациональные и действительные значения. Без числовой башни
паритет невозможен.

## Как устроены преобразования в Java

`TypeRegister` хранит граф преобразований и ищет кратчайший путь BFS. Рёбра
регистрируются инициализаторами типов:

- `natural -> integer`, `integer -> natural`;
- `integer -> rational`, `rational -> integer`;
- `integer -> real`, `real -> integer`;
- `rational -> real`, `real -> rational`;
- `real -> complex`;
- `integer -> gaussian`, `gaussian -> complex`.

Важно: часть рёбер **неточная или случайная**:

- `rational -> integer` в Java идёт через `FInteger.div` и для положительного
  знаменателя ведёт себя как округление вниз, а не как обычное отбрасывание
  дробной части;
- `real -> integer` использует `floor`;
- `real -> rational` выбирает случайный знаменатель от 1 до 1000;
- `integer -> natural` на отрицательном числе бросает ошибку.

Поэтому копировать этот граф как «неявные приведения» опасно: решатель может
получить разные состояния из одного выражения, а `natural` перестанет быть
строгим. В C++ предлагается разделить:

- **безопасные расширения** — используются при сопоставлении сигнатур;
- **явные преобразования** (`to rational`, `to integer`, ...) — только по
  команде автора/игрока;
- **неточные преобразования** — не участвуют в неявном выборе перегрузки и не
  меняют тип цели.

## Предлагаемая числовая башня

### Точные типы

```
natural  ⊂  integer  ⊂  rational
integer  ⊂  gaussian  ⊂  complex
rational ⊂  real      ⊂  complex
```

Расширения, которые не теряют значения:

- `natural -> integer`, `integer -> rational`, `integer -> gaussian`;
- `rational -> complex` (если `complex` строится из точных компонент);
- `gaussian -> complex` (целые компоненты точно переводятся в real при
  достаточной точности);
- `real -> complex` (пара `(x, 0)`).

`rational -> real` и `real -> rational` — неточные; их лучше делать явными.
`real -> integer`, `rational -> integer`, `integer -> natural` — сужения,
которые проверяются на границе и не должны происходить молча.

### Представление

Минимальный вариант для C++17 — `boost::multiprecision::cpp_int` для больших
целых (header-only). Если зависимость нежелательна, нужен собственный `BigInt`,
но это отдельный крупный проект.

```cpp
using BigInt = boost::multiprecision::cpp_int;

struct Natural  { BigInt value; };
struct Integer  { BigInt value; };
struct Rational { BigInt num, den; };       // den > 0, gcd(num, den) = 1
struct Gaussian { BigInt re, im; };

struct Real {
    // Вариант 1: десятичное число с фиксированной точностью/масштабом.
    BigInt unscaled;
    int scale = 0;
    // Вариант 2: строка/нормализованный decimal.
};

struct Complex { Real re, im; };
```

`Value` остаётся `std::variant` или становится классом с явным тегом. Для
решателя важны:

- каноническое равенство (`Value::same`) — тип + нормализованное значение;
- согласованный с ним хеш;
- полный порядок для сортировки состояния;
- отсутствие `NaN`/бесконечностей или явная их поддержка с отдельными
  правилами.

Для `rational` канонизация обязательна: знак только у числителя, деление на
НОД, нулевой знаменатель — ошибка домена. Для `real` нужна одна выбранная
точность и правило округления. **Нельзя** одновременно сравнивать `real` с
эпсилоном и хешировать точное значение: в Java `FReal.equals` использует
`EPS = 0.0001`, а `getHash` — точный `BigDecimal`; это несогласованно и для
решателя недопустимо.

### Формат `.lvl`

Тип уже задаётся у каждого числа, поэтому синтаксис расширяется естественно:

```text
number natural 3
number integer -5
number rational 3/4
number real 1.25
number gaussian 2+3i
number complex 1.5-2i

answer rational 7/3
```

Требования к парсеру:

- `rational=3/4` и `number rational 3/4` дают одно и то же;
- `gaussian=2+3i` — два целых, `complex=1.5-2i` — два действительных;
- отрицательная мнимая часть не должна терять знак;
- `real` хранится в каноническом виде, чтобы `1.20` и `1.2` были одним
  значением;
- `natural` по-прежнему не принимает отрицательное.

Отображение: `rational 3/4`, `real 1.25`, `gaussian 2+3i`, `complex 1.5-2i`.
Для mixed-набора, как и сейчас, полезны имена (`number rational 3/4 as q`).

## Влияние на вычисления

- `commonType` становится операцией поиска наименьшего общего типа в решётке,
  а не «natural + natural, иначе integer».
- `sum/sub/mul/div` для rational считаются точно; `div` для integer остаётся
  целочисленным, как в текущей модели, а для rational — точная дробь.
- `mod` имеет смысл только для целых (natural/integer/gaussian?); для rational
  и real его нужно либо запретить, либо определить отдельно.
- `pow` для rational может давать огромные числители/знаменатели; нужен лимит
  или отказ, а не насыщение.
- `root`/`log` для natural/integer — целочисленные (см. 0024); для real —
  приближённые с выбранной точностью.
- `abs`, `sign`, `min`, `max`, `norm`, `conj`, `arg` должны иметь сигнатуры
  для каждого типа, а не только для integer.

Ошибка типа или домена (нулевой знаменатель, корень чётной степени из
отрицательного, переполнение лимита) не должна ронять программу: она
возвращается как диагностика (0019), а решатель отбрасывает неудачный исход.

## Влияние на решатель

Числовая башня увеличивает пространство состояний:

- `rational` растёт по числителю/знаменателю, но остаётся точным;
- `real` может порождать бесконечно много значений; нужен конечный набор
  литералов/операций и канонизация;
- `complex`/`gaussian` добавляют два измерения;
- `pow`, `fact`, `root` могут давать очень большие числа.

Практичные ограничения:

- точные типы (`natural`, `integer`, `rational`, `gaussian`) — основной режим
  решателя;
- `real`/`complex` — отдельный режим уровня с явным лимитом точности и
  запретом бесконечных серий преобразований;
- ключ состояния использует канонические значения, а не исходные строки;
- `Value::same` и хеш должны быть согласованы, иначе DFS будет терять или
  дублировать состояния;
- для `real` либо точное каноническое равенство, либо отказ от `real` в
  уровнях, где важна проверка цели.

## Поэтапный план

1. **BigInt для natural/integer.** Убрать `long long`/`kLimit`, переписать
   `asLongLong` на `toBigInt`, оставив проверяемое преобразование для UI.
   Это уже закрывает большую часть различий с Java.
2. **Rational.** Точная нормализация, парсинг `a/b`, арифметика, хеш.
3. **Gaussian.** Пара BigInt, `re`/`im`, точные операции.
4. **Real.** Фиксированная точность, канонизация, явные правила округления,
   `floor`/`ceil`, тригонометрия при необходимости.
5. **Complex.** Пара `Real`, `re`/`im`, `conj`/`arg`/`norm`.

Порядок важен: сначала точные типы, потом приближённые. Иначе решатель получит
нестабильные цели раньше, чем появится нормальная канонизация.

## Что затронет

- `src/Value.h` — вариант/класс, равенство, порядок, хеш, `toBigInt`;
- `src/Functions.*` — `commonType`, сигнатуры, арифметика, новые функции;
- `src/Function.*` — типы параметров/выходов, литералы, `use`-алиасы;
- `src/LevelStore.*` — парсинг и запись чисел всех типов;
- `src/Solver.*` — ключи состояний, лимиты, эвристики;
- `src/Level.*` — ввод чисел и проверка целей;
- `CMakeLists.txt` — зависимость `Boost.Multiprecision` или собственный BigInt;
- `data/levels/`, `docs/game.md`, `docs/level-authoring.md`.

## Риски

- `boost::multiprecision` увеличивает время компиляции и требует зависимости;
  свой BigInt — ещё больше кода и тестов.
- `real` с эпсилоном ломает хеш и DFS; нужно выбрать точную канонизацию.
- `rational`/`fact`/`pow` быстро раздувают состояния.
- Старые уровни и сохранения должны остаться совместимыми.
- Нельзя ослабить `natural`: отрицательный результат — ошибка, а не
  автоматическое превращение в integer.
- Числовая башня и структурные значения (0009) — разные проекты; не стоит
  делать их одним изменением.
