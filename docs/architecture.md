# Архитектура и карта кода

Этот документ — для разработчика, который впервые открывает C++-исходники.
Он объясняет, как модули связаны, где проходит граница между данными и
вычислениями и какие инварианты нельзя ломать. Пользовательская документация
по уровням и функциям — в [`game.md`](game.md) и
[`level-authoring.md`](level-authoring.md).

## 1. Общая картина

Проект состоит из четырёх слоёв:

```text
main.cpp
  ├─ Game / Level            игровой цикл и команды
  ├─ LevelStore              чтение/запись .lvl и .fn
  ├─ Function / Functions    функции: сигнатуры, тела, вычисление
  └─ Solver                  поиск решения для hint и --check
```

Поток данных одного уровня:

```text
levelN.lvl
  │  LevelStore::load
  ▼
LevelData { числа, имена, функции, ответ }
  │
  ├─ Level::play        интерактивное прохождение
  └─ solver::solve      проверка/подсказка
```

`LevelData` — «холодные» данные уровня. `Level` — изменяемое состояние
прохождения: текущий набор, история, стек откатов. `Fn` — функция уровня;
`fmath::FunctionSpec` — встроенная простейшая функция из реестра.

## 2. Базовые понятия

### Значение

`src/Value.h`.

```text
Num = Value = variant<Natural, Integer>
```

Тип хранится **у каждого числа**, а не у уровня. `natural` не может быть
отрицательным; `integer` может. `Value::same()` и `operator==` сравнивают и тип,
и число, поэтому `natural 1` и `integer 1` — разные значения. Числовые
операторы (`value == 1`) сравнивают только величину и нужны для удобства.

### Набор и ход

Набор уровня — мультимножество чисел. Функция забирает аргументы из набора и
добавляет результаты. Порядок чисел в наборе не важен; для решателя он
канонизируется сортировкой, чтобы одинаковые состояния не пересчитывались.

Ход в `Level` хранится не отдельной структурой, а снимком набора в
`stack_`; история — строками для показа игроку. В `solver` ход описывается
структурой `solver::Move`.

### Сигнатура и результаты

`src/Functions.h`.

- `Signature` — типы аргументов и `ResultSpec`.
- `ResultSpec` — фиксированные результаты + необязательный поток в конце.
  Например, `primes` — это `natural...` (ноль или больше результатов), а
  гипотетическая `divmod` может быть `integer integer`.
- `canPass(from, to)` разрешает точное совпадение и расширение
  `natural → integer`; обратное преобразование возможно только проверяемо, при
  вычислении.
- `FunctionSpec::apply` вычисляет один детерминированный результат.
- `FunctionSpec::allOutcomes` перечисляет возможные результаты случайной
  функции; для стабильных он пуст, и используется `apply`.

### Виды функций уровня

`src/Function.h`.

1. **Известная** — имя совпадает с поведением в реестре (`sum`, `primes`).
2. **Неизвестная** — у неё своё имя (`A`, `B`), но поведение скрыто. Игрок
   видит только описание; в данных хранится `behavior`.
3. **Пользовательская** — блок `function … end`; у неё есть параметры, выходы,
   тело и, возможно, несколько перегрузок.

`Fn` — это функция уровня. Для простейших она ссылается на `behavior`; для
пользовательских хранит `overloads`.

## 4. Загрузка уровня

`levelstore::load` в `src/LevelStore.cpp`:

1. Читает файл как UTF-8-байты и режет на строки.
2. Пропускает пустые строки и `#`-комментарии.
3. Разбирает `number`, `numbers`, `answer`, `function`.
4. Для `function <имя>` делает lookahead: если следующая значимая строка —
   `description`/`in`/`out`/`use`/`body`, это начало пользовательского блока.
5. `parseFunctionBlock` собирает сырой `FunctionBlock` и требует `end`.
6. `function <имя> file <файл>` читает `data/functions/<файл>.fn` и подставляет
   блок, переименовывая его в имя уровня.
7. Все пользовательские блоки передаются в `compileFunctionBlocks`, который
   проверяет структуру и добавляет `Fn` в `LevelData::functions`.
8. Проверяются обязательные части: числа, ответ, хотя бы одна функция; имена
   чисел не должны совпадать с функциями.

Важно: на этапе загрузки проверяется **структура** блоков, но не типы всех
выражений. Типы и домены проверяются при вычислении. Это осознанный первый
шаг; статическая типизация тел — будущая работа.

### Формат `.lvl`

Подробности и примеры — в [`level-authoring.md`](level-authoring.md). Кратко:

```text
# комментарий
number natural 84 as n
answer natural 42
function sum
function A unknown mul
function myfn
  description ...
  in n: natural
  out r: natural
  body
    r = mul n natural=2
end
```

`save` старается сохранять старый компактный формат (`numbers`/`answer`), если
все числа `integer` и имён нет. Иначе пишет `number <тип> <значение> [as имя]`.
Пользовательские функции сохраняются через `formatFunctionBlock`, поэтому
`load → save → load` не должен терять блоки.

## 5. Прохождение уровня

`Level` хранит:

- `pool_` — текущий набор `PoolItem { value, name }`;
- `original_` — начальный набор;
- `stack_` — снимки набора для `back`;
- `history_` — строки выполненных ходов;
- `completed_` — найден ли ответ.

Имя числа — метка. Она помогает игроку вводить число и выбирать экземпляр, но
решатель работает только со значениями. После хода имя исчезает вместе с
числом; у результатов имён нет.

### Разбор выражения

Ввод игрока сначала проходит через `Level::prepareExpression`:

- если строка начинается с известной функции, в ней нет бинарного инфикса и
  нет вызова `f(...)`, сохраняется старый путь `wordsFromString` (префикс,
  скобки и запятые как разделители);
- иначе `expression::normalize` разбирает инфикс, `f(...)`, скобки и запятые и
  переписывает выражение в те же префиксные слова.

Нормализация ничего не вычисляет: `Expression.cpp` — отдельный лексер и
рекурсивный парсер с приоритетами `+ -`, `* / %`, `**`. Благодаря этому
типизация, потоки, случайность и решатель остаются в существующих модулях.
Смешивать префиксный вызов и инфикс в одном выражении нельзя.

`Level::evalExpression` — рекурсивный разбор уже префиксной записи:

- токен-функция: набирает аргументы, пока не получит `numberOfArgs` значений;
  вложенный вызов может вернуть несколько результатов и заполнить сразу
  несколько аргументов (`mul primes 77`);
- токен-имя: ищет число с такой меткой в наборе;
- токен-литерал: `natural=2` / `integer=2` или голое число;
- при `consumeFromSet=true` аргументы удаляются из рабочей копии набора.

`applyExpression` сначала работает с копией `pool_`. Если выражение разобрано
целиком и без ошибки, копия становится новым набором, результаты добавляются,
ход пишется в историю, а снимок кладётся в `stack_`. Поэтому ошибка не портит
текущий набор.

`calc` использует тот же разбор с `consumeFromSet=false`: имена читаются, но
числа не удаляются; литералы создаются по типу.

Тела пользовательских функций нормализуются вторым проходом в
`Function.cpp`, когда известны все функции и алиасы: так `sum 1 2` остаётся
префиксом, а `a + b` становится `sum a b`.

### Команды

`Level::turn` — диспетчер команд. Сначала проверяет, нет ли ответа уже в
наборе; затем читает строку. Служебные команды (`help`, `nums`, `calc`,
`back`, `reset`, `hint`, `exit`) обрабатываются отдельно, остальная строка
считается выражением и передаётся в `prepareExpression`. Ошибка разбора не
меняет набор.

## 6. Реестр простейших функций

`src/Functions.cpp`, `buildRegistry()`.

Каждая встроенная функция получает:

- список `Signature`;
- `apply` — реализацию;
- `stable`;
- для случайных — `allOutcomes`.

Бинарные арифметические функции имеют две сигнатуры:

```text
natural × natural → natural
integer × integer → integer
```

`canPass` позволяет передать `natural` туда, где ожидается `integer`, поэтому
смешанный вызов обслуживается integer-сигнатурой. `primes` — унарная функция с
потоком: `natural → natural...` и `integer → integer...`.

Случайные функции (`rand`, `sumr`, `subr`, `mulr`, `divr`) помечены
нестабильными. `binaryOutcomes` перечисляет все допустимые результаты; для
очень широких диапазонов `rand` выбирает прореженную сетку (`kMaxOutcomes`),
чтобы DFS не раздулся. Это точка, которую нужно менять при другой стратегии
перебора случайности.

`factorize` — пробное деление до `sqrt(value)`, с проверкой отрицательных
значений. `primes` возвращает простые множители с повторениями.

## 7. Пользовательские функции

### Компиляция

`compileFunctionBlocks`:

1. Проверяет имена, запрещает переопределять встроенные функции и специальные
   формы (`take`, `drop`, `first`, `rest`, `count`).
2. Группирует блоки с одинаковым именем — это перегрузки.
3. `prepareOverload` проверяет параметры, выходы, алиасы, строки тела,
   уникальность имён и полноту присваивания выходов.
4. Собирает `Fn` с `overloads`.
5. Проверяет цели `use`-алиасов после добавления всех функций, чтобы алиас мог
   ссылаться на функцию, объявленную позже.
6. Проверяет, что локальные имена не совпадают с функциями.
7. Распространяет нестабильность по графу вызовов до неподвижной точки:
   функция, вызывающая `rand` или нестабильную пользовательскую функцию,
   становится нестабильной.

### Runtime

`Fn::use` выбирает перегрузку и вызывает `runBody` в обычном режиме.
`Fn::outcomes` — в режиме `allOutcomes`, где каждый случайный вызов может дать
несколько альтернатив.

`runBody`:

- создаёт окружение `Env = map<имя, vector<Num>>`;
- связывает параметры, проверяя/приводя типы;
- выполняет присваивания по порядку;
- если выражение дало несколько альтернатив, размножает окружения;
- ограничивает число альтернатив и глубину рекурсии;
- собирает выходы в порядке объявления.

`evalExpr` имеет фиксированный приоритет:

```text
специальная форма → алиас → функция уровня → встроенная функция
→ литерал → переменная окружения
```

`evalCall` набирает аргументы **по значениям**, а не по синтаксическим
выражениям: один вложенный вызов с потоком может дать несколько аргументов.
Алиасы дополнительно проверяют типы и приводят `natural → integer` перед
вызовом цели.

`selectOverload` считает score по точным совпадениям типов. Точное совпадение
важнее расширения; равный лучший score у разных перегрузок — ошибка.

## 8. Решатель

`src/Solver.cpp`.

Состояние — отсортированный вектор значений. `signature` строит хеш
мультимножества; `dead` хранит состояния, из которых решение не найдено,
`active` — текущий путь (защита от циклов).

DFS:

1. Если цель уже в наборе — успех.
2. Проверить лимиты узлов/времени.
3. Отсечь состояние по `signature`.
4. Сначала попробовать все функции в режиме «только один ход до цели».
5. Затем — полный перебор функций и аргументов.
6. После неудачи пометить состояние в `dead`.

Для арности 1–2 одинаковые значения группируются: выбирается представитель
группы, потому что замена одного экземпляра на другой даёт то же
мультимножество. Для большей арности используется упорядоченный выбор индексов.

Ограничение `valueBound` отсекает промежуточные числа, которые сильно больше
цели и входных данных; это эвристика, а не доказательство нерешаемости.
`--check` может не найти решение за лимит — это не всегда означает, что
уровень нерешаем.

## 9. Сохранения

- Уровни: `data/levels/levelN.lvl`.
- Пользовательские функции: `data/functions/<имя>.fn`.
- Описания встроенных функций: `data/functions.txt` (`имя описание`).
- Игроки: `data/players/players.txt` и `data/players/<hash>.sav`.
- Оценки сложности: `data/lvlrate.dat`.

Пароли хранятся как FNV-1a-хеш; это учебный проект, не криптографическая
защита. `promptLine` в `Player.cpp` обрабатывает EOF и CRLF.

## 10. Как расширять

### Добавить простейшую функцию

1. Реализовать `Value op...` в `Functions.cpp`.
2. Добавить имя в `buildOps()`.
3. Если функция нестабильна — добавить её в `isUnstableName` и реализовать
   ветку в `binaryOutcomes`.
4. Добавить описание в `data/functions.txt`.
5. Проверить `--check` на уровнях, где она встречается.

### Добавить новый тип

1. Добавить альтернативу в `ValueType` и `Value`.
2. Обновить `valueTypeName`, `valueTypeFromName`, `Value::of`, `asLongLong`
   (или добавить отдельный доступ).
3. Обновить `canPass` и `commonType`.
4. Проверить `ResultSpec`, парсеры `.lvl`/`.fn`, отображение и решатель.

### Изменить стратегию перебора

Основные точки: `binaryOutcomes` (какие исходы случайности перебирать),
`Search::tryFunction` (какие наборы аргументов), `Search::dfs` (порядок и
отсечения). Лимиты и `valueBound` — эвристики; не превращайте их в
единственный критерий корректности.

### Добавить команду уровня

Добавить ветку в `Level::turn` и, если нужно, метод в `Level`. Не забыть, что
ошибка команды не должна менять `pool_`.

## 11. Инварианты и ограничения

- `pool_` и `LevelData::numbers` — мультимножества; порядок не семантичен.
- Ошибка вычисления не должна частично менять набор уровня.
- `natural`-результат не может быть отрицательным.
- У функции должен быть хотя бы один выход; поток — только последний.
- Каждый выход получает значение ровно один раз.
- Пользовательская функция не переопределяет встроенную.
- Имена локальных значений не совпадают с функциями.
- Один поток результатов; несколько потоков — будущая работа.
- `if`/`bool`, `sort`/`shuffle` и статическая типизация тел не реализованы.
- `abs`/`not` остаются бинарными ради старых уровней.
- `take`/`drop`/`first`/`rest`/`count` доступны в телах функций, но не как
  обычные команды уровня.

## 12. Проверка изменений

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
```

`ctest` запускает `tests/expression_tests.cpp` и по одному тесту на каждый
уровень. Уровень 18 пока исключён: полный `--check` возвращает код `1` из-за
известного ограничения DFS. Для одного уровня код `0` означает, что решение
найдено.

CI в `.github/workflows/ci.yml` повторяет эти шаги на Windows/MSVC,
Linux/GCC и macOS/AppleClang. Релизный workflow
`.github/workflows/release.yml` запускается по тегу `v*`, собирает архивы
через CPack и прикрепляет их к GitHub Release.

Полезные smoke-тесты:

```sh
# редактор функции
printf 'name f\nin n: natural\nout r: natural\nbody r = mul n natural=2\ntest natural=6\nexit\n' \
  | ./funcmath --function

# ручное прохождение уровня 79
printf 'test\np\np\nlevel 79\nsplit n\nmul 3 7\ndouble 21\n0\nexit\n' \
  | ./funcmath
```

При изменении формата `.lvl` проверьте round-trip: загрузить уровень,
сохранить через `levelstore::save` и загрузить снова. При изменении
пользовательских функций — `validate`/`test` в `--function`.
