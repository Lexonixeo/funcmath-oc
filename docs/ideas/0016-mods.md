# 0016. Моды: новые простейшие функции и типы

**Статус:** идея
**Сложность:** высокая

## Суть

Мод добавляет в игру новые простейшие функции, уровни и, в перспективе, новые
типы значений. Пользовательские функции уровня (0015) для этого не подходят:
они собираются из уже существующих простейших и не расширяют движок.

## Уровни поддержки

### 1. Декларативные моды

Файлы `.fn` с функциями из существующих простейших:

```text
mods/my-mod/mod.toml
mods/my-mod/functions/triple.fn
mods/my-mod/levels/level1.lvl
```

Плюсы: безопасно, кроссплатформенно, без загрузки кода.
Минус: не добавляет новых простейших; полезно скорее как библиотека
разделяемых функций, чем как полноценный мод.

### 2. Нативные плагины (C ABI)

Дают новые простейшие функции, доступ к системе, максимальную скорость.
Минус: доверенный код, платформозависимость, риск падения и читов.

Эскиз:

```cpp
extern "C" const FuncmathMod* funcmath_mod();

struct FuncmathMod {
    const char* id;
    const char* version;
    int api_version;
    void (*register_functions)(Registry*);
};
```

Регистрация функции — существующий `FunctionSpec`: сигнатуры входов/выходов,
`apply`, `outcomes`, `stable`.

### 3. Скриптовые плагины

Lua/Wren/JS-песочница: проще и безопаснее нативных плагинов, но нужна
интеграция интерпретатора и ограничение возможностей.

## Новые типы

Это намного сложнее, чем новые функции. Понадобится:

- расширить `Value` (variant или динамический payload);
- парсинг/сериализация значений в `.lvl`;
- равенство, порядок, хеширование для решателя;
- отображение в консоли и UI;
- таблица преобразований типов;
- арифметика и другие операции над новым типом;
- поддержка в `Solver`, `Level`, `LevelStore`, `LevelGenerator`.

Поэтому порядок лучше такой:

1. новые типы в ядре (вектор, строка, запись) — без плагинов;
2. API функций для модов;
3. ABI типов для модов, если действительно понадобится.

Тип-плагин должен уметь хотя бы: parse, print, compare, hash, clone,
serialize, deserialize и, возможно, преобразования в другие типы.

## Изоляция имён

Функции и уровни мода получают namespace:

```text
my-mod.triple
my-mod/level1
```

Это защищает от коллизий с базовыми именами. В `.lvl` можно ссылаться на
`function my-mod.triple`.

## Манифест и версии

```toml
id = "my-mod"
name = "My Mod"
version = "1.0.0"
api_version = 1
dependencies = []
```

Нужны проверки совместимости API, зависимостей и версий. Для мультиплеера —
одинаковый набор модов и чексуммы у сервера и клиентов.

## Безопасность и мультиплеер

- нативные моды — доверенный код; на сервере не грузить untrusted;
- скрипты — sandbox, лимиты времени/памяти;
- подписи/чексуммы модов, whitelist на сервере;
- скрытые функции мода остаются на сервере, клиент получает только метаданные;
- сервер проверяет все ходы, не доверяет клиентским модам;
- случайность — серверный seed, иначе мод может подкручивать исходы.

## Что затронет

`src/Functions.*`, `src/Function.*`, `src/Value.h`, `src/LevelStore.*`,
`src/Level.*`, `src/Solver.*`, `src/main.cpp`, новый загрузчик модов,
`docs/game.md`.

## Риски

- ABI нестабилен, пока движок быстро меняется;
- новые типы ломают формат уровней и решатель;
- безопасность нативных модов;
- моды могут сделать игру нечестной в мультиплеере.
