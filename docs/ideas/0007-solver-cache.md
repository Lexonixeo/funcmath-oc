# 0007. Кэш решателя: готовые шаги вместо повторного DFS

**Статус:** идея
**Сложность:** средняя

## Суть

Сейчас `hint` и `--check` каждый раз запускают DFS с нуля. Если уровень уже
когда-то решался, это лишняя работа: можно сначала попробовать **готовое
решение**, а DFS запускать только как запасной вариант.

Предлагается двухуровневый кэш.

### 1. Кэш решений (то, что предложил пользователь)

Для уровня хранится один или несколько найденных путей — последовательность
ходов. Перед запуском DFS:

1. Взять сохранённый путь.
2. **Проиграть его** на текущем уровне: проверить, что каждое число есть в
   наборе, функция доступна, ход легален.
3. Если путь дошёл до цели — вернуть его (или первый ход для `hint`).
4. Если путь не подошёл (уровень изменился, скрытая функция ведёт себя иначе,
   случайный исход другой) — запустить обычный DFS.

Именно так и сформулирована идея: «проверять по уже готовым шагам; если по ним
не получается почему-то, то делать прогон по DFS».

### 2. Кэш состояний (transposition table)

Во время DFS запоминать состояния:

```
(набор чисел, доступные функции, поведения скрытых функций) -> результат
```

Результат: «решения нет», «решение есть за N ходов», «лучший ход». Если такое
состояние уже встречалось, повторно его не перебираем. Это ускоряет и
`hint`, и `--check`, и будущую генерацию уровней.

Состояние — мультимножество, поэтому числа перед ключом сортируются.
Для случайных функций в ключ нужно включать политику исходов или хранить
результат с пометкой «вероятностно».

## Где хранить

Варианты:

- `data/cache/` — рабочий кэш, создаётся автоматически, в git не попадает
  (уже добавлен в `.gitignore`);
- `data/solutions/` — **предвычисленные** решения официальных уровней, которые
  можно коммитить: тогда `hint` работает мгновенно сразу после клонирования.

Формат — простой текст/JSONL:

```
# ключ = hash(содержимое уровня + версия движка + политика случайности)
level 3
path sum 2 5 | mul 7 1
moves 2
```

Для каждого уровня можно хранить несколько путей (разные стратегии) и выбирать
самый короткий.

## Инвалидация

Кэш обязательно привязан к:

- содержимому `.lvl` (числа, цель, функции, скрытые поведения);
- версии движка/решателя;
- политике случайности (`rand`, `sumr`, …).

Если хэш не совпал — кэш игнорируется и перестраивается. Это защищает от
ситуации «уровень поправили, а подсказка осталась старая».

## Эскиз

```cpp
struct CachedSolution {
    std::string levelHash;
    std::vector<Move> moves;
};

std::optional<Solution> Solver::solve(const LevelData& level) {
    if (auto cached = cache_.find(level); cached && replay(level, *cached)) {
        return cached;                 // готовые шаги подошли
    }
    auto fresh = dfs(level);           // запасной вариант
    if (fresh) cache_.put(level, *fresh);
    return fresh;
}
```

CLI:

- `--no-cache` — игнорировать кэш (полезно для отладки);
- `--rebuild-cache` — пересчитать кэш для всех уровней;
- `--check` — по умолчанию сначала кэш, потом DFS.

## Зачем

- `hint` отвечает мгновенно на уже решённых уровнях.
- `--check` перестаёт быть линейным по времени при каждом запуске.
- Уровень 18 достаточно решить один раз (вручную или более умным поиском),
  после чего он не будет «не найден» при каждой проверке.
- Кэш состояний — основа для оценки сложности и генерации уровней заданной
  сложности (см. идею 0010).

## Риски

- Устаревший кэш опаснее медленного поиска → обязательный хэш и проверка
  каждого хода при проигрывании.
- Для случайных уровней «готовый путь» может требовать конкретных исходов;
  нужно хранить их или явно помечать путь как вероятностный.
- Кэш состояний может занимать много памяти; нужны лимиты и LRU/обрезка.
