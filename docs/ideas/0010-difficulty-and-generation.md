# 0010. Сложность уровня и генерация под заданную сложность

**Статус:** идея
**Сложность:** высокая

## Проблема

В письме руководителю отмечено: при генерации уровня сложности >100 уровень
может проходиться **легче**, чем уровень сложности 5–10. Причина — сложность
сейчас задаётся параметрами генератора (размер чисел, количество функций), а не
измеряется по самому уровню.

Нужна метрика, которая монотонно связана с реальной трудностью, и генератор,
который умеет попадать в заданный диапазон.

## Метрики сложности

Предлагается считать сложность из свойств уровня и результатов решателя:

| Метрика | Что показывает |
|---------|----------------|
| `min_moves` | минимальное число ходов до цели (кратчайшее решение) |
| `branching` | сколько в среднем легальных ходов из состояния |
| `state_space` | оценка числа достижимых состояний |
| `dead_end_ratio` | доля тупиковых веток |
| `unknown_count` | число скрытых функций |
| `random_count` | число случайных функций (дисперсия) |
| `solution_count` | сколько разных решений (чем меньше, тем сложнее) |
| `human_score` | успешность/число попыток/время игроков |

Формула — взвешенная сумма с нормировкой, например:

```
difficulty = w1 * min_moves
           + w2 * log(1 + state_space)
           + w3 * dead_end_ratio
           + w4 * unknown_count
           + w5 * random_count
           + w6 * (1 / (1 + solution_count))
```

Веса калибруются по данным игроков. Шкала — 1–100 (или 1–10), важно, чтобы она
была **монотонной**: более сложный уровень не получает меньший балл.

## Генерация под сложность

Два подхода:

### 1. Генерация + измерение + отбор

1. Сгенерировать уровень с параметрами, соответствующими целевому диапазону.
2. Решить его (с кэшем из идеи 0007) и посчитать метрики.
3. Если сложность вне допуска — отбросить и повторить.
4. Накопить несколько кандидатов и выбрать ближайший к цели.

Плюс: просто. Минус: может долго не попадать в узкий диапазон.

### 2. Обратная генерация

1. Взять целевую численность набора и набор функций.
2. Начать с целевого числа и применять **обратные** операции, получая
   правдоподобные исходные числа.
3. Проверить, что прямой поиск действительно находит решение за нужное число
   ходов.
4. Скорректировать сложность, добавляя/убирая «лишние» числа и функции.

Плюс: уровень гарантированно решаем. Минус: обратные операции есть не у всех
функций (`mod`, `rand`, `abs`).

### 3. Комбинированный

Обратная генерация для каркаса + измерение метрик + отбор.

## Практические шаги

1. Реализовать `--check --metrics`: для каждого уровня печатать `min_moves`,
   `branching`, `state_space`, `solution_count`.
2. Собрать данные на 62 уровнях и вручную упорядочить несколько уровней по
   ощущению сложности.
3. Подобрать веса так, чтобы метрика согласовывалась с ручным порядком.
4. Добавить `--generate --difficulty N` с допуском и лимитом попыток.
5. Добавить телеметрию (по желанию): сколько попыток/времени тратят игроки.

## Зачем

- `random D` перестанет врать: D будет означать реальную сложность.
- Новые уровни можно генерировать целенаправленно, а не «как получится».
- Появится объективная шкала для прогресса и достижений.
- Решатель и кэш (0007) дают для этого готовую инфраструктуру.

## Риски

- Сложность субъективна; метрики — приближение.
- Точный `state_space` считать дорого; нужна оценка.
- Генерация с проверкой может быть медленной; кэш и лимиты обязательны.
- Нельзя допустить, чтобы «сложность» росла только из-за больших чисел.
